# P0 UI 性能与窗口恢复回归复盘

日期：2026-08-28
影响版本：提交 `a49b3b0` 之后、修复提交之前的本地 Release 构建
状态：已修复并加入防复发约束

## 摘要

P0 UI 收尾期间连续出现三类回归：文件列表点击被覆盖层拦截、窗口尺寸在高 DPI 环境下被错误持久化并在下次启动继续放大、Windows Release 意外显示控制台窗口。最严重时 AsterFiles 恢复为约 `13013 × 13688` 的渲染表面，常驻内存约 4.4 GB，导致窗口持续高 CPU、点击和绘制明显卡顿。

修复后，同一会话的空闲常驻内存约 116 MB，窗口无控制台子窗口，文件列表恢复单击选择与双击打开。

## 用户可见症状

- 文件夹双击无效，文件行不能可靠响应鼠标。
- UI 启动后持续迟缓，明显差于 `a49b3b0` 基线。
- 通过快捷方式运行 Release 时出现独立 Console 窗口。
- 会话恢复后的窗口尺寸异常，并会跨启动持续存在。

## 根因

### 1. 输入覆盖层遮挡列表

为支持“单击空白处清除选择”，在文件列表容器顶部放置了全区域 `TouchArea`。Slint 的后绘制项参与命中测试时位于上层，因此它吞掉了行内的单击与双击。

### 2. 物理像素与逻辑像素混用

会话保存直接记录 `Window::size()` 返回的物理像素，恢复时又把该值按窗口尺寸使用。在高 DPI/多屏环境中，每次保存和恢复都会再次应用缩放。错误状态最终写入 `%LOCALAPPDATA%\AsterFiles\session.bin`，形成约 `13013 × 13688` 的窗口记录。Skia 为巨大窗口分配渲染资源，造成数 GB 内存与持续重绘。

### 3. 高频交互触发全量 UI 重建

单击一行后调用 `refresh_ui`，重新创建整个文件列表及其他模型；侧栏还每 5 秒无条件刷新全部 UI。这不是本次数 GB 内存的主因，但显著放大了交互迟滞。

### 4. Windows 子系统声明缺失

Release 二进制仍使用默认控制台子系统，直接运行或通过快捷方式启动时会附带终端窗口。

## 为什么没有及时发现

- 只验证了截图和功能结果，没有在同一 Release 进程上记录 CPU、内存、窗口尺寸和子进程。
- 没有执行“退出保存 → 再次启动恢复 → 再退出”的 DPI 会话往返测试。
- UI 改动后没有对命中测试层级做真实双击验证。
- Debug 与 Release 验证产物一度不一致，导致用户运行到旧构建。
- 性能门槛被安排在 P6，但基础交互阶段仍需要最低回归护栏；这一点执行不足。

## 修复

- 空白区点击层移动到列表下方，文件行保持最高输入优先级。
- 窗口大小统一以逻辑像素持久化；保存时用缩放因子从物理像素换算。
- 对历史异常尺寸增加恢复上限，超过 `7680 × 4320` 时回到默认窗口。
- 单击选择只更新旧行、新行和状态摘要，不再重建完整模型。
- 移除侧栏每 5 秒的无条件全量刷新。
- 删除每行 Tooltip，降低大量可见项的额外 UI 对象成本。
- Windows 构建声明 GUI 子系统，不再创建 Console 窗口。

## 回归证据

修复后 Release 实测：

- 空闲工作集约 116 MB，私有内存约 54 MB；问题版本工作集最高约 4.4 GB。
- 5 秒采样期 CPU 累计约 0.64 秒，随后保持空闲。
- 子进程数 0，Console 窗口数 0。
- `cargo test --quiet`：22 项通过。
- `cargo fmt -- --check`：通过。
- `cargo clippy --all-targets --all-features -- -D warnings`：通过。
- `cargo build --release`：通过。

## 防复发规则

### 每次窗口/会话改动必须验证

1. 100%、150%、200% 缩放至少覆盖两档。
2. 连续执行两次“启动 → 改尺寸/位置 → 退出 → 再启动”，逻辑尺寸不得增长。
3. 恢复数据必须有合理上限；非法或异常值回到安全默认值。
4. 位置使用物理屏幕坐标，尺寸明确使用逻辑像素，代码和数据结构不得含糊混用。

### 每次列表/输入层改动必须验证

1. 单击选中、双击打开、悬停、滚动和空白处清除选择都要在真实桌面程序验证。
2. 全区域 `TouchArea` 必须位于交互子项下方；禁止在列表上方放透明捕获层。
3. 高频交互不得调用全量 `refresh_ui`；优先更新受影响行或局部状态。
4. 周期任务不得无条件刷新完整 UI；只有数据实际变化时才提交差异。

### 每次 Release 交付必须验证

1. 直接运行用户指定的 `target/release/asterfiles.exe`，不能用 Debug 截图代替。
2. 启动后记录窗口尺寸、CPU、工作集、私有内存、线程和子进程。
3. 静置 5 秒后 CPU 应回落，普通目录内存不得显著高于认可基线。
4. Windows GUI 交付不得出现 Console 窗口。
5. 报告 Release 的时间戳与 SHA-256，确保用户运行的是同一产物。
6. 结束验证后清理所有 AsterFiles 及辅助调试进程。

## 后续自动化

- 为 `WindowPlacement` 增加逻辑尺寸边界与异常恢复单测。
- 增加 Release 冒烟脚本：启动、采样资源、检查子进程/Console、退出并再次启动。
- 在 P6 性能门槛前，先保留轻量基线：普通根目录空闲工作集约 116 MB；超过基线 2 倍或持续占用一个 CPU 核即视为回归。
- 为主要 UI 区域增加真实鼠标冒烟检查，覆盖列表行和背景命中顺序。
