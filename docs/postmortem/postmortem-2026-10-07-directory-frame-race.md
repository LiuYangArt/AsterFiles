# 目录帧删除竞争复盘（#138）

## 症状

默认并发测试中，301 项目录曾在 257 项后中断。只有一个健康文件的库来源也曾收到完成帧后退出 101。单项重跑通过，降低并发也不能证明已修复。此前子进程标准错误被丢弃，无法从旧日志恢复当时的原始错误。

## 根因与证据边界

父进程删除批次文件，表示页面已经消费。子进程通过 `GetFileAttributesW` 查询文件是否消失。即使查询不打开文件句柄，也可能与 Windows 删除过程重叠并返回 `ERROR_ACCESS_DENIED`（5）。旧实现将其作为传输失败，测试子进程随后 panic；该路径既可能发生在数据帧后，也可能发生在完成帧后。

本次在同一 Windows 环境用真实文件删除和属性查询并发复现，29 次创建／删除内捕获错误码 5。结果保存在 `artifacts/logs/issue-138/delete-race.json`，复现脚本为同目录 `delete-race.py`。这证明当前确认逻辑存在实际竞争；旧日志未保留 stderr，不能断言每次历史失败均由同一错误码引起。

## 修复

确认查询遇到拒绝访问时继续等待，槽位仍视为占用。仅文件或路径明确不存在才确认消费。其他查询错误原样返回；不降低并发，不放宽完整性断言。持续拒绝访问由父进程原有无进度超时和取消机制回收。成功仍同时要求完成帧与子进程成功退出。

辅助进程 stderr 写入独占临时文件，测试进程开启错误栈。失败时保留非空原始文件并在父进程日志中输出其路径和内容；正常及空日志清理。传输错误带写入、发布或确认阶段，保留 Windows 错误码。

## 回归与后续排查

`issue_138` 测试覆盖 4096 次真实并发删除、受控错误码 5 连续出现时的等待、确认后槽位复用、持续拒绝访问的超时和取消回收，以及完成前后 panic 的原始错误和错误栈。完整验证仍运行默认并发的 `python tools/verify.py`，包含目录、库加载和无界面场景以及 Debug 构建。结果以 `artifacts/verify/summary.json` 和 Issue 评论为准。

排查先定位父进程日志中的 `stderr=` 路径，再查看原始错误阶段、系统错误码及 `completed`。不要只看退出 101，也不要将完成帧视为子进程成功退出。真实网络速度和界面交互仍由用户验收。

诊断期间另发现首批耗时 700 ms 的墙钟断言偶发失败，真实子进程已成功退出。该问题另记 #153，证据为 `artifacts/logs/issue-138/reproduce-2.log`，不混入本次竞争修复。
