# Everything 集成回归与验收复盘

日期：2026-08-30  
影响范围：Everything E1–E3、智能地址栏、搜索状态机、分页排序、名称高亮与文件列表布局  
状态：已修复并完成自动验证

## 摘要

Everything 首版完成连接后，真实使用连续暴露出范围查询为零、地址栏范围前缀消失、搜索结果与目录模型串页、十万级结果无界加载、退出搜索状态残留、滚动操作意外取消搜索、排序方向与 Everything UI 不一致，以及高亮片段撑出大空格和名称列居中/跨列等问题。

这些问题并非单个刷新遗漏，而是协议语义、页面状态所有权、分页策略和 Slint 布局约束同时缺少真实端到端验收。最终实现收敛为：官方 Query2 IPC、范围和用户表达式分离、页面来源与请求代次隔离、按滚动触发的有界分页、与 Everything 会话一致的独立搜索排序、文件/文件夹双服务端组合分页，以及官方高亮标记投影。

## 用户可见症状

- `ancestor:"F:\CodeProjects\AsterFiles\docs" (*.md)` 返回零项，而 Everything/ES 在同一目录能找到结果。
- 点击或继续输入后，地址栏只剩查询词，当前完整路径前缀消失；光标落在最左侧。
- 全局 `.md` 显示 133186 个结果，但列表仍是原目录；退出后目录计数和“父目录”列仍残留搜索状态。
- 后台尝试拉取十万级全部结果，输入明显卡顿，列表和内存工作无界增长。
- 拖动搜索结果滚动条、点击结果或地址框失焦会退出搜索。
- AsterFiles 表头显示“名称 ↑”，对照的 Everything 会话实际是名称降序，首屏顺序因此不一致。
- 高亮后出现“高级    功能计划.md”“_    high    level”等虚假空格；超长名称可能碰到父目录列。
- 修复紧凑高亮时，普通目录名称又被布局容器居中，图标和名称没有保持左侧连续排列。
- 运行中的 Debug 程序锁住 `target/debug/asterfiles.exe`，统一验证首次重建时报 `Access is denied`。

## 根因

### 1. 用通用引号假设代替 Everything 函数参数实证

最初把目录范围拼成 `ancestor:"路径"`，只验证了全局搜索，没有用真实 Query2 对范围搜索验收。本机 Everything 1.5a 的 `ancestor:` 参数不能按该形式引用，导致实现表面可用、核心范围场景实际返回零项。

最终改为按 Everything 官方字符实体编码函数参数，路径中的空格、引号、括号、操作符、Unicode 与 UNC 保持原义；用户高级表达式完全独立，不按空格拆分或改写。

### 2. 展示文本与搜索状态混用

地址栏组合文本、内部范围和用户查询曾共用同一字段。UI 双向绑定与 `refresh_ui` 重新投影时，查询词会覆盖“原始路径 + 空格 + 查询”，也无法可靠区分“删除完整前缀切换全局”和“路径本身包含空格”。快捷键还曾保留单独的路径全选分支，使交互出现两套状态。

最终只保留统一智能编辑转换：点击空白、`Ctrl+L`、`Alt+D` 均保存独立 `SearchScope + query`，展示层组合完整文本，首次进入只聚焦到末尾。

### 3. 目录和搜索没有完整的页面所有权

早期总数、条目、列模式和错误字段没有全部以 `PageSource` 隔离。搜索第一页到达时列表仍可能绑定旧目录；Escape 只关闭编辑状态，没有失效请求和恢复目录快照，迟到页仍有机会污染页面。

最终搜索结果严格校验 `TabId + RequestId + PageSource`；进入搜索时保存目录条目、选择和焦点快照，第一页立即替换模型；退出时取消并递增请求身份，恢复目录快照、普通列、目录计数与选择。

### 4. 把“分批协议”误实现成“后台拉完再提交”

worker 曾以 128 项循环获取 133186 个结果，直到完成后才统一提交，同时每批触发 UI 刷新。这违反大列表有界加载要求，也为未显示结果生成大量领域对象和 UI 投影。

最终每页限制 256 项，首批立即显示；只有滚动接近末尾时提交下一页，取消后不再续页。条目 ID 使用全局 offset，跨页保持稳定。

### 5. 地址框焦点被错误当作搜索生命周期

Slint 中覆盖内容区的透明 `TouchArea` 和 `AddressEditor` 失焦回调都会调用取消。滚动条、结果行和内容区因此既被遮挡，又会意外终止搜索。

最终移除全屏取消层和失焦取消；搜索只由 Escape、取消按钮、明确导航或标签生命周期结束。

### 6. 排序对照方向错误，且 UI 分组不属于 Query2 sort_type

初次审计只确认 Query2 `NameAscending` 与 `es -sort name-ascending` 相同，却拿它对比 Everything 当前名称降序页面，错误怀疑区域语言或自然排序。`Session-1.5a.json` 后来直接证明 `.md/.blend` 标签为 `sort="Name", sort_ascending=0, sort_mix=0`。

同时，Query2 `sort_type` 只表达字段与方向，不承载 Everything UI 的文件/文件夹分组。若只对每页本地重排，会在跨页边界产生重复、遗漏或错序。

最终搜索使用独立排序状态，默认名称降序以匹配当前 Everything 会话，不改变普通目录排序。每种字段和方向都由 Query2 服务端排序；同一高级查询分别附加受保护的 `file:` 与 `folder:` 条件，通过各自 total 和 offset 组合为“文件优先、文件夹后置”的稳定分页。

### 7. 高亮算法和 Slint 布局都重复发明了已有能力

最初在本地从查询字符串猜测字面匹配，无法完整复现高级语法。随后使用占满父列宽的 `HorizontalLayout` 放置多个固定宽度文本，剩余空间被分配到片段之间，产生看似文件名含大空格的视觉错误。改为 preferred width 后又因布局对齐规则使普通目录名称居中。

最终请求官方 `EVERYTHING_IPC_QUERY2_REQUEST_HIGHLIGHTED_NAME`，解析 `**` 字面星号和 `*text*` 高亮标记；标记只用于展示，原始名称和路径仍是身份。外层名称单元格占满列宽并裁剪，内层布局从 `x=0` 开始、`alignment: start`、片段不伸展；图标固定在左侧，名称紧贴图标，超长内容显示省略号且不跨列。

### 8. 自动验证与视觉验收边界不清

编译和单元测试通过曾被过早解释为交互与布局已正确；初次截图没有进入精确搜索场景，也不能证明排序、高亮和滚动行为。用户真实截图因此成为发现问题的主要入口。

此外，UI 截图残留的 AsterFiles 进程锁住 Debug 可执行文件，导致第一次 `verify.py` 失败。失败不是代码错误，但说明调试进程清理应当是验证流程的一部分。

## 修复结果

- 唯一正式连接保留为专用消息窗口 + WM_COPYDATA Query2，无 DLL 或递归回退。
- `ancestor:` 范围按官方字符实体编码，Unicode、UNC、空格和操作符路径不改变查询含义。
- 三种地址栏入口统一，路径前缀、查询和光标位置稳定。
- 搜索第一页立即投影，滚动触发下一页；十万级查询保持有界。
- 搜索退出完整恢复目录状态，迟到页按请求与页面来源丢弃。
- 搜索排序独立于普通目录；默认名称降序匹配本机 Everything 会话。
- 文件/文件夹以两个服务端稳定集合组合分页，不进行单页本地分组。
- 官方 Query2 高亮替代本地猜测；片段连续、左对齐、裁剪且不跨列。
- 普通目录和搜索结果都保持“图标 + 名称”左侧连续排列。
- 文件夹大小仍只使用索引结果，并区分 0、未索引、超时与断开。

## 防复发规则

1. Everything 查询语法必须用真实 Query2 验证全局、范围、空格路径、Unicode、UNC 和高级语法；ES CLI 只作交叉证据。
2. 搜索范围、用户表达式和组合展示文本必须是三个明确概念，禁止按空格反向拆解路径。
3. 新页面数据必须携带 `TabId + RequestId + PageSource`；附属回填再增加条目 ID 和原始路径。
4. 大结果集必须先显示有界首批，并由真实滚动需求触发续页；禁止后台自动拉完。
5. 服务端分页顺序不能用单页本地重排修补；需要分组时必须建立稳定的服务端子集合和跨集合 offset。
6. 排序对照必须先核对双方字段、方向和视图设置；表头箭头属于验收证据的一部分。
7. Everything 已提供的高亮、排序和结果字段优先直接请求，不从查询字符串猜测成熟产品语义。
8. Slint 分段文字必须验证剩余空间分配、左对齐、长文本裁剪和相邻列边界；普通目录与搜索态都要截图。
9. 地址框焦点不是搜索生命周期；滚动、选择和失焦不得隐式取消页面。
10. 编译和领域测试不能替代真实 UI 验收。涉及焦点、滚动、列布局或富文本时，必须保留精确场景截图。
11. 运行 UI 验证后先关闭调试进程，再执行最终构建和哈希检查，避免 Windows 文件锁造成误报。
