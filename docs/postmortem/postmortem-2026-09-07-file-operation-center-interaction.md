# Issue #62 文件任务中心交互回归复盘

日期：2026-09-07

影响范围：大目录复制、文件任务中心

状态：已修复并由用户确认

## 摘要

任务中心从单任务窗口扩展到多任务展示后，连续出现了窗口样式和高度回归、进度不更新，以及暂停、取消和关闭需要多次点击的问题。最终根因不是文件复制本身慢，而是进度事件持续在 UI 线程重建任务列表：一方面挤占输入处理，另一方面可能在鼠标按下与松开之间替换按钮所在行，导致一次完整点击丢失。

## 用户可见症状

- 实际窗口被陈列室的多状态布局撑高，并出现多余底色和分隔线。
- 大目录扫描或复制期间，暂停、取消和右上角关闭需要多次点击。
- 一度为了降低刷新压力而移除进度刷新，导致进度条完全不更新。
- 关闭窗口曾只隐藏任务，但主界面没有可靠入口重新打开，形成不可见的后台任务。

## 根因

1. 陈列室和真实窗口共用尺寸及列表刷新路径，演示需求影响了实际窗口。
2. 每个进度事件都向 UI 线程投递刷新，并重新创建完整 Slint 列表模型。高频刷新会积压，也会替换正在接收点击的组件。
3. 取消只依赖上层轮询。目录扫描、暂停等待和 Windows 单文件复制没有全部共享同一条即时取消信号。
4. 诊断日志只挂在主窗口，最初无法判断任务窗口是否收到第一次按钮回调。
5. 产品语义没有结合入口能力验证：隐藏窗口合理的前提是用户随时能重新打开，而当时并不成立。

## 修复

- 陈列室固定为独立演示高度；真实窗口按实际任务数收紧，最多显示三行并滚动。
- 进度状态先在后台合并，UI 同一时刻最多保留一次待处理刷新。
- 复用同一个任务列表模型，只更新变化行，不在持续进度中重建窗口和列表。
- 暂停改为明确设置目标状态并等待工作线程确认，重复请求保持幂等。
- 取消统一唤醒暂停等待，并把信号直接传给 Windows `CopyFile2`；扫描和进度上报发现取消后立即停止。
- 右上角关闭与取消使用一致语义：取消活动任务并关闭窗口，不产生不可见后台任务。
- 为暂停、取消和关闭回调补充诊断事件，后续能区分“系统收到点击”和“业务回调执行”。

## 失败方案及教训

仅降低刷新频率不能解决组件被替换的问题；直接删除刷新又会让进度停住。正确做法是把高频状态提交和低频结构变化分开：状态更新合并并原地提交，只有任务增删、语言或主题变化才刷新窗口结构。

本次还说明，陈列室必须只消费演示数据，不能反向决定真实窗口尺寸或生命周期；交互语义也必须与当前可发现入口配套，不能孤立套用“关闭只隐藏”的常见模式。

## 回归验证

- 用户使用约 6 GB、约 1.38 万文件的大目录完成真实复制、暂停和取消复测，确认首次点击响应恢复正常。
- `python tools/verify.py --quick`：通过，汇总位于 `artifacts/verify/summary.json`。
- Issue 收尾由 `tools/finish-issue.ps1` 执行完整无界面验证及本地 Release 构建。

## 防复发规则

1. 进度、下载、索引等高频事件不得反复替换包含交互控件的列表模型。
2. UI 事件队列中的高频刷新必须合并，任一时刻最多保留一个待处理刷新。
3. 进度刷新只更新变化行；任务结构、窗口尺寸和静态文案使用独立的低频刷新路径。
4. 暂停和取消必须覆盖扫描、等待、系统调用和上报边界，并保持重复请求幂等。
5. “关闭只隐藏”必须先有稳定、可发现的重开入口，否则关闭应结束对应后台操作。
6. 陈列室的演示高度、演示状态和真实窗口生命周期必须隔离。
7. 窗口交互诊断必须记录目标窗口的按钮回调，不能只记录主窗口鼠标消息。
