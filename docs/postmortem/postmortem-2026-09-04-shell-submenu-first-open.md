# Issue #46 Windows Shell 子菜单首次展开与点击失效复盘

日期：2026-09-04

影响范围：Windows 快速菜单的 Shell 子菜单首次展开、异步加载、附属窗口创建、分支切换与叶子命令执行

状态：已修复并由用户在真实 Windows 窗口确认

## 摘要

快速菜单中的 `New`、TortoiseSVN 等 Shell 子菜单曾出现三类相互关联的症状：首次悬停不展开、点击父项时崩溃，以及子菜单已经显示但点击叶子项偶发无响应。关闭整份菜单再打开通常恢复。

最终日志证明，首次悬停时 Shell 内容加载正常，真正失败的是子菜单附属窗口第一次创建后的原生句柄尚未就绪。Slint 组件对象已经返回，但同一事件回调中立即取得的 HWND 仍可能为零，owner 绑定因此失败；旧流程随即关闭子菜单分支，稍后到达的合法 Shell 结果无窗口可投影。第二次打开时 HWND 已经生成，所以表现为“重开后恢复”。

最终修复把内容加载、窗口建立和首帧呈现视为三个独立阶段。原生窗口尚未就绪时不丢弃 Shell 请求，而是在下一帧有限重试；窗口先以 cloak 状态显示，内容加载完成后更新当前分支，再完成首帧呈现。

## 用户可见症状

- 进入应用后第一次把鼠标停在 `New` 上，箭头高亮但子菜单不显示。
- 点击尚未展开的 `New` 曾导致应用崩溃。
- `New`、TortoiseSVN 等子菜单中的选项偶发点击无响应。
- 移到另一个带子菜单的项目，或关闭整份菜单再打开后，原项目通常恢复。

## 诊断证据

首次复现的日志依次显示：

1. 悬停事件正常到达，250ms 展开计时器正常触发。
2. `New` 的 Shell 子菜单请求正常发出。
3. Windows Shell 在约 211–256ms 内返回 7 项，身份校验通过。
4. 结果投影被跳过，因为当前菜单会话中没有已建立的子菜单窗口分支。

增加窗口建立阶段日志后，最终复现记录为：

```text
quick_menu_submenu_open_retry
reason=attach_owner:popup owner is unavailable
```

约 24ms 后，同一个打开动作记录 `quick_menu_submenu_opened`，随后 Shell 内容正常显示。根菜单当时已经可见，owner 主窗口也有效，因此失败对象是刚创建的子菜单 HWND，而不是主窗口或 Shell 加载。

证据文件：`artifacts/logs/window-interaction-diagnostic.jsonl`

## 根因

### 1. Slint 组件创建完成不等于 HWND 已可用

`QuickSubmenuWindow::new()` 返回后，底层 Windows 窗口可能要到后续事件循环才完成实例化。旧流程在同一回调中立刻取句柄并绑定 owner。首次创建时句柄可能为零，绑定失败；同一深度的窗口对象仍然保留，下一次打开时句柄已有效，因此问题具有明显的“只在第一次发生”特征。

### 2. 窗口暂时未就绪被误当成永久失败

旧流程在 owner 绑定、cloak 或 show 任一步失败后立即关闭分支和子菜单状态。Shell 加载在另一线程继续进行，结果虽然合法，却找不到当前窗口槽，只能跳过投影。用户看到的便是完全没有反应，而不是加载提示或延迟展开。

### 3. 内容、分支与窗口呈现的状态曾耦合过紧

异步 Shell 请求身份、菜单分支身份和原生窗口生命周期是三套不同状态。把“窗口此刻是否可显示”作为接受 Shell 结果的前提，会把短暂的窗口建立延迟放大为永久丢失。

### 4. 深层分支激活与可变状态借用边界不完整

子菜单切换过程中，父层叶子项在后代打开时仍应能够执行；旧判定只允许最深层激活。部分回调还在持有窗口状态借用时再次进入同一状态容器，形成崩溃风险。

## 修复

- 子菜单窗口首次 owner 绑定、cloak 或 show 遇到暂时失败时，保留当前 Shell 请求，并以 16ms 间隔最多重试两次。
- 重试成功后继续使用同一个分支和加载结果，不要求用户移开鼠标或重新打开菜单。
- 加载期间窗口保持 cloak；内容投影到当前窗口槽后，再请求重绘、刷新合成器并解除 cloak。
- Shell 结果只按 Shell 会话、请求、token 与当前标签页请求校验；窗口槽只负责呈现。
- 异步加载完成时同步替换窗口槽持有的行快照，避免视觉内容与点击命令身份不一致。
- 父层叶子项即使已有后代子菜单，也能先关闭后代再执行当前分支命令。
- 将可能重入的窗口状态读取与后续 UI 调用拆开，避免可变借用期间再次进入同一状态容器。
- 主动点击和键盘打开会取消待处理的悬停；悬停计时器回调不再同步取消自身。
- Debug 诊断日志固定写入仓库 `artifacts/logs`，不再受启动工作目录影响。

## 未奏效的判断与教训

最初仅根据“Shell 结果已返回但投影跳过”，把问题归因于悬停计时器在回调中取消自身。移除这处重入后仍可复现，说明它只是风险点，不是最终根因。

关键转折是继续给窗口建立阶段分段记录，而不是再猜测加载速度或增加更早预加载。日志证明：

- 不是没有开始加载；
- 不是加载完成后没有数据；
- 不是单个第三方 Shell 扩展故障；
- 是首次 HWND 尚未就绪时，把可恢复的瞬态失败当成了终止条件。

## 防复发规则

1. UI 组件构造成功不代表原生 HWND 已经可用；首次访问句柄必须允许跨一个事件循环就绪。
2. owner 绑定、cloak 和首次 show 的瞬态失败应有限重试，不得立即销毁仍有效的异步请求。
3. 重试必须有明确上限、阶段日志和会话校验；旧菜单关闭后不得复活窗口。
4. Shell 内容身份、菜单分支身份和 HWND 生命周期分开管理，不能互相代替有效性判断。
5. 异步结果接受后，模型、窗口槽行快照和点击命令身份必须在同一次投影中更新。
6. 父层分支有后代时，点击父层叶子项应先失效后代，再执行父层命令。
7. Windows 首次窗口呈现问题必须以真实日志和用户手动验证收尾；自动测试只能覆盖状态与身份规则。
8. “第二次正常、第一次失败”优先检查惰性原生资源实例化，不要先归因于加载慢或缓存。
