# Issue #82 大目录永久删除复盘

日期：2026-09-11

影响范围：永久删除、后台空间释放、任务中心

状态：已修复并由用户确认

## 摘要

永久删除最初只优化了“把目录从列表移走”，但来源移除、递归清理、任务恢复和任务窗口仍耦合在一起。连续删除会被上一批清理阻塞；内部清理目录可能进入普通目录模型并显示“响应错误”；重启会把未完成清理误报为失败；任务窗口会打断操作，而且关闭和进度反馈不可靠。

最终把永久删除拆成两个独立阶段：前台只负责持久记录和同卷原子移动，后台由全局单一清理通道串行释放空间。任务中心不自动弹出，窗口关闭只收起，来源移除后不提供无法恢复数据的暂停或取消。

## 用户可见症状

- 第一批大目录仍在释放空间时，第二批永久删除原路径不能立即消失。
- `.asterfiles-cleanup` 出现在文件列表并显示“响应错误”。
- 重启后任务中心残留多条 `cleanup interrupted before completion` 失败任务。
- 删除成功后自动弹出任务窗口；窗口的最小化、关闭、暂停和取消语义混乱。
- 自绘 X 收不到可靠的关闭效果；后台清理长期显示“已处理 0 项”。

## 根因

1. 来源移除和递归清理共用本地任务槽，清理时间直接阻塞下一次提交。
2. 内部清理路径没有成为全局保留命名空间，目录读取、搜索、文件夹大小和文件操作仍可触达它。
3. 启动恢复把“进程中断”当成业务失败，而不是继续执行持久记录中的剩余工作。
4. 任务窗口沿用了普通复制任务的暂停、取消和自动弹窗模型，没有考虑永久删除已经不可恢复。
5. 自绘 X 先调用应用回调直接隐藏窗口，没有走 Slint 的窗口关闭协议；日志显示点击已到达，但可见状态未可靠改变。
6. 递归清理只在整个顶层目录结束时提交统计，因此单个大目录处理期间一直显示 0。
7. 增量进度加入后，取消和失败路径一度会重复累计已上报数据；完成记录写入和记录目录删除之间也存在重启残留窗口。

## 修复

- 新增独立清理资源和工作线程：本地提交完成原子移动后立即释放，后台清理保持全局串行。
- 用自有版本化记录保存任务身份、原始路径、遗留路径、稳定文件身份和阶段；多实例通过独占认领避免重复清理。
- `.asterfiles-cleanup` 及后代在目录、搜索、大小调度、导航和文件操作入口统一过滤。
- 重启后自动恢复有效清理任务；恢复型任务默认不污染任务中心，真实错误仍保留重试入口。
- 永久删除不自动打开任务窗口；来源移除后隐藏暂停和取消；完成后短暂显示“空间已释放”。
- 任务窗口只保留 X，自绘 X 调用 Slint `close()`，由统一的 `CloseRequestResponse::HideWindow` 收起窗口，后台任务不变。
- 清理过程按时间、项目数或字节阈值增量提交项目、容量和当前路径，并复用既有的 UI 合并刷新。
- 进度统计由单一结算器维护基线，避免取消、失败和重试重复累计；启动恢复会清除零剩余项的完成记录。

## 失败方案及教训

- 仅把目录快速改名，但仍在同一任务里递归删除，只改善第一批的表象，无法支持连续删除。
- 为快速路径设置大小或项目数阈值需要先递归扫描，反而把等待搬到删除之前。
- 把进程退出直接映射为失败会制造伪错误；持久后台工作应恢复剩余动作，而不是恢复旧进程状态。
- `hide()` 返回成功不等于自绘关闭路径的窗口生命周期正确；自绘按钮必须进入框架自己的关闭协议。
- 只在顶层项目结束时上报进度对大目录没有意义；进度边界必须位于递归工作内部，同时限频避免重现 Issue #62 的 UI 刷新回归。

## 防复发规则

1. 不可恢复操作的“提交”和“后台回收资源”必须是独立状态与独立调度边界。
2. 内部工作目录必须在所有入口按路径身份过滤，不能依赖隐藏属性或展示名称。
3. 可恢复后台任务只持久化剩余工作和稳定身份，不能持久化瞬时进程状态。
4. 自绘窗口按钮必须走窗口框架的关闭协议；字符串接线测试需同时覆盖按钮入口和原生处理端。
5. 递归任务的进度在递归内部增量产生，并限频后进入 UI；不能以顶层目录完成作为唯一上报点。
6. 增量累计必须只有一个所有者；取消、失败和重试不得再次叠加已提交快照。
7. 完成记录与记录目录删除之间的崩溃窗口必须由下次启动幂等收敛。
