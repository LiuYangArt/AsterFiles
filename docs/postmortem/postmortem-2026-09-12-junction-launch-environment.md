# Issue #109：联接创建失败与启动环境的对照

## 症状与结论

调查 #102 时，由 Codex 启动的自动程序在用户 Temp 下通过目录联接新建目录，返回 Windows 错误183（文件已存在），实际目标没有该目录；用户在 Explorer 中创建成功。

2026-09-12，用户在独立 PowerShell 中运行同一个已编译 Rust 探针，真实目标、联接长路径、扩展路径、短路径四项均成功。随后 Codex 再运行同一探针，真实目标成功，三种联接路径仍失败183。将工作目录改为用户相同的 C:/Windows/System32，结果不变。所有结果同时检查实际目录是否存在，成功项清理自己的空目录。

差异与启动环境关联；不能归因为 Rust、短路径或 C: Temp 的普遍限制。具体涉及令牌、作业、虚拟化还是文件系统过滤机制尚未查明。独立程序仍可能继承启动环境，不能仅凭“独立小程序也失败”排除环境因素。

## 决策与边界

没有修改 AsterFiles 的目录创建逻辑，不忽略183，不增加备用创建方式，不调整系统安全设置。生产使用的 std::fs::create_dir 在用户独立启动的探针中正常；这不是整个应用的真实界面验证，也不保证所有启动环境均正常。

联接入口位于用户 Temp 时，Codex 下完整路径创建失败；入口位于用户主目录或 D: 仓库 artifacts 时成功，九种入口/目标位置组合排除了目标卷决定结果的解释。先打开联接父目录再按相对名称创建成功，但没有证据证明 Explorer 使用该实现；不将此探查方式移入产品。

## 长期排查方法

1. 在同一受控联接、同一个可执行程序下对比自动环境与用户独立终端；名称必须唯一。
2. 同时保存错误码和实际目标存在性，不能只看命令退出码。.NET/PowerShell 在本轮自动环境中曾报告成功但未实际创建。
3. 保留原始路径，对照长名、短名、扩展路径及工作目录，避免把相关性写成根因。
4. 只清理探针自己创建的对象；先移除联接本体，确认真实目录边界后再处理测试目标。
