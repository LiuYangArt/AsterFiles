# P3 操作完成反馈与列表选择回归复盘

日期：2026-08-31
影响版本：提交 `bdb1dca` 及其开发过程中的 Debug 构建
修复提交：`26af40b`
状态：已修复，用户已完成真实窗口确认

## 摘要

P3 补充“复制或移动完成后选中最终目标”时，先出现目标焦点短暂闪现后消失；修复该问题后，又连续破坏普通单击、`Ctrl+单击` 和 `Shift+单击`。自动测试均通过，但用户在真实窗口中两次指出选择行为仍不正确。

最终确认这是两个相互独立、但都属于“同一次手势或刷新只有一个状态所有者”的问题：

1. 目录刷新提交会清空选择，操作完成目标必须在清理之后、且仅在匹配的刷新中恢复。
2. 拖动候选在鼠标按下时提前修改选择，随后点击回调再次修改，导致一次手势执行两次选择。

## 用户可见症状

- 复制文件后，新文件短暂获得焦点，随即取消选中。
- 第一次修复后，点击不同文件会保留旧选择，看起来自动进入多选。
- 普通单击不能稳定形成单选。
- `Ctrl+单击` 离散多选和取消选择异常。
- `Shift+单击` 连续范围选择异常。

## 根因

### 1. 操作完成焦点设置与刷新提交顺序相反

操作完成事件先记录最终目标，再触发目录刷新。目录读取完成时先尝试设置目标选择，但 `commit_path` 随后执行统一的 `clear_selection`，因此焦点只在一帧内出现。

正确顺序应是：

1. 校验 `TabId + RequestId + 原始目录`；
2. 提交刷新结果并执行既有选择清理；
3. 仅当存在匹配的待选目标时，一次性设置 `selected`、`focused` 和 `selection_anchor`；
4. 将稳定焦点滚入可见区域。

### 2. 把普通目录刷新误改为保留选择

第一次修复直接让 `NavigationKind::Refresh` 不再清空选择。这扩大了语义：目录监听、F5 和操作刷新都会保留旧选择，而条目 ID 在重新枚举后仍可能对应可见条目，于是普通点击的结果会被后续刷新带回，表现为自动多选。

操作完成反馈是一次特定刷新携带的附加意图，不应改变所有刷新行为。

### 3. 鼠标按下与点击回调重复修改选择

为准备应用内拖动，`begin_internal_drag` 在鼠标按下时发现当前行未选中，立即执行普通单选。松键后 Slint 的 `clicked` 又根据当次 `Ctrl`、`Shift` 执行一次选择。

结果是同一手势被处理两次：

- 普通点击：按下先单选，松开再单选；
- `Ctrl+单击`：按下先单选，松开再切换，状态被反转；
- `Shift+单击`：按下先重设锚点，松开无法使用原锚点选择范围。

这一缺陷早于复制焦点改动存在，但本轮连续修改选择与刷新链路后才被真实测试集中暴露。

### 4. 自动测试只覆盖状态函数，没有覆盖事件序列

已有测试证明 `select_entry` 的普通、切换和范围规则正确，也证明操作完成刷新能选中目标，但没有模拟：

- `pointer down → drag candidate → click` 的完整顺序；
- 目录刷新清理与操作完成待选恢复的先后关系；
- 用户点击与目录监听刷新交错。

因此测试验证了各个局部函数，却没有证明一次真实手势只修改一次选择。

## 修复

- 恢复所有目录刷新原有的选择清理语义。
- 操作完成待选集合绑定 `TabId + RequestId + 原始目录`，只在对应刷新提交并清理之后恢复。
- 多项成功一次性写入选中集合，最后一个成功项获得稳定焦点和选择锚点。
- 鼠标按下只建立拖动候选路径快照，不再修改当前选择。
- 按下已选行时拖动现有多选；按下未选行时拖动该行路径，但不提前改变界面选择。
- 未跨过拖动阈值时，唯一的选择变更来自点击回调，并保留普通、`Ctrl`、`Shift`、`Ctrl+Shift` 语义。

## 防复发规则

1. 一次鼠标手势只能有一个选择状态所有者：按下负责建立候选，点击负责选择，跨阈值后拖动负责执行拖放。
2. 禁止在 `pointer down` 和 `clicked` 两处同时修改 `selected`、`focused` 或 `selection_anchor`。
3. 特定操作的刷新后反馈必须作为绑定请求的附加意图实现，不得改变所有 `Refresh` 的通用语义。
4. 刷新后选择恢复必须发生在刷新提交和统一清理之后。
5. 选择相关改动必须覆盖普通、`Ctrl`、`Shift`、`Ctrl+Shift`，并验证点击与拖动阈值两条事件序列。
6. 状态函数单测不能替代事件序列测试；至少验证“按下未移动后松开”和“按下跨阈值后拖动”。
7. 用户报告真实交互与自动测试矛盾时，优先检查事件是否重复投递、状态是否被后续刷新覆盖，不再只检查最终状态函数。
8. Release 前必须由真实窗口确认核心选择手势；Codex 继续遵守禁止自动化操作 AsterFiles UI 的约束。

## 2026-09-05 再次回归：非活动窗口三击与首次右键

Issue #53 的真实窗口验收又发现两类相关表现：AsterFiles 窗口失焦后，文件列表第一次双击只能选中，第三次才进入目录；文件或目录第一次右键只能激活窗口，第二次才弹出菜单。侧栏快速访问和空白处没有相同问题。

根因是文件列表行同时承担普通点击、内部拖动候选和右键菜单。非活动窗口收到首次鼠标输入时，winit 先产生 `Focused(true)`；原处理立即重载快速访问并刷新全部窗口，替换了文件行控件，打断了这次点击序列。右键还先进入内部拖动候选，菜单依赖释放阶段的结束回调，激活阶段丢失释放事件后就只能第二次触发。

修复采用两条明确边界：窗口从非活动变为活动时不重载或刷新文件列表，避免在鼠标手势中替换列表投影；文件列表右键按下直接提交条目菜单，右键不进入拖动候选，左键仍负责点击与拖动。这样新建后的定向聚焦仍可在对应刷新完成后执行，但不会拥有或重放当前鼠标手势。

防复发规则补充：

1. `Focused(true)` 不得同步或异步刷新会承载当前鼠标手势的主列表。
2. 文件列表右键菜单不能依赖内部拖动释放回调；首次右键必须和侧栏、空白处具有相同的激活行为。
3. 每次真实验收必须覆盖非活动窗口的首次单击、双击和右键，并与活动窗口结果对照。
