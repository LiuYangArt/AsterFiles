# 网络目录排序与加载提示闪现复盘（#141、#143）

## 症状与影响

进入网络目录时，文件先按错误顺序出现，读完后再重排。用户反馈本地目录没有相同观感。排序修复后，中央“正在加载…”仍会快速闪过。

两种现象都发生在首批内容出现前后。用户同时要求慢网络不能阻塞窗口，仍能切换本地目录、取消或关闭标签。

## 根因

### 首批显示与最终排序使用了不同规则

目录批次原来按枚举顺序追加。显示层再按旧行数追加新增条目，直到完成事件才读取目标目录偏好并统一排序。网络辅助进程先交付首项，再逐批交付，未排序的中间状态因此更容易暴露。

本地目录共用这条追加路径。读取较快可以解释为什么不容易看到跳变，但本次没有据此断言所有本地目录都不会出现问题。

此前测试分别验证“完成前能看见批次”和“最终排序正确”，没有验证每批可见顺序。只给暂存列表排序也不够：如果显示层仍按旧行数截取尾部，会漏掉插入前方的文件，或重复显示旧文件。

### 加载状态直接触发了中央文字

中央文字原来随 Loading 状态立即显示。很快到达的首批内容又会移除文字，形成短暂闪现。加载状态本身仍需准确保留，不能为了隐藏文字而伪装成加载完成。

## 修复与保留的边界

首批即采用目标目录偏好。每批只排序新条目，再按已有名称、类型、大小和时间合入有序列表；相同规则下，完成事件不再重新排序。名称等比较只使用内存数据，不补查网络元数据。

列表按文件身份插入新行。分组和网格只更新文件显示区域，同步页面状态和排序指示。加载中改变排序立即作用于可见条目，并保存到目录偏好。完成时保留有效选择与滚动位置；恢复选择前先由最终列表剔除已不存在的身份。

中央加载提示独立延迟 500 ms。快速收到首批内容时不显示，持续等待时才显示；首批、空目录、错误或取消结果即时生效。导航或切换标签产生新的显示代次，计时回调还要核对窗口、标签、请求和当前状态，避免旧提示覆盖新页面。

网络读取、辅助进程等待、批次确认和取消回收继续由原有后台资源处理。没有等待全目录读完再显示，没有增加 UI 线程网络访问，也没有用休眠实现提示延迟。原始路径身份、过期请求拒收、单槽背压和网络超时策略保持不变。

## 回归证据

#141 的 9 项回归覆盖五种排序字段与升降序、目标目录偏好、多批合并、加载中改排序、选择和滚动、分组与网格、迟到结果，以及等待确认时的取消和本地导航。

#143 的 6 项回归使用模拟时间，覆盖 499/500 ms 边界、刷新不重置等待、首批即时显示、空目录与错误、取消和关闭、连续导航及切换标签。测试使用 Slint 无窗口后端，不控制桌面窗口。

此前完整 Debug 验证通过；加入提示延迟后的快速验证为 896 项通过、0 项失败、7 项忽略。既有 #103、#104 测试覆盖真实辅助进程的受控慢源、挂起、取消、回收与本地来源隔离。用户反馈排序已恢复，随后接受当前提示处理并要求收尾。

十万条目、391 批的内存测试记录：合并总耗时 1151 ms，单批峰值 10 ms；已有十万条目后新增 256 项，合并为 5 ms，列表模型更新为 27 ms。这些数据不包含原生窗口绘制，不能当作真实 NAS 延迟或所有视图的响应上限。

## 后续排查入口

- 顺序只在完成时改变：检查 `src/domain.rs` 的增量合并和 `src/app.rs` 的首批偏好、完成提交，确认期间没有切换排序规则。
- 出现重复或遗漏：对照待显示条目与文件模型的身份序列，检查插入位置，不能仅比较条目总数。
- 已有内容仍显示加载文字：检查首批后的页面状态和 `src/app/loading_hint.rs`，不要通过延迟内容来隐藏文字。
- 切换标签后出现旧提示：核对窗口、标签、请求与显示代次，确认计时只修改提示属性。
- 慢网络下操作不响应：先区分后台 I/O 等待与主线程模型更新时间，分别检查 #103/#104 隔离回归和 #141 性能输出。

以后的分批加载改动必须验证中间状态。排序和插入应共同验证，延迟提示应与真实加载状态分开；不能仅以最终列表正确作为通过依据。
