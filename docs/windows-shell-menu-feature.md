# Feature：Windows Shell 菜单集成

> 日期：2026-08-31
> 状态：Issue #13 第一阶段与普通子菜单按需展开已实现并通过自动验证；真实 UI 验收及其余第二阶段能力待完成；不属于 P3

## 0. Issue #13 实施状态（2026-09-01）

采用“Slint 快速菜单外壳 + Windows 经典菜单数据 + 原生完整菜单兼容出口”。当前 Debug 已完成第一阶段：右键立即显示搜索框和 AsterFiles 自有命令；专用可复用 STA 工作线程在同一线程创建、使用和释放 `IContextMenu`/`HMENU`，后台读取顶层普通项目；会话标识、菜单请求代次、标签与目录请求身份、原始路径和选择快照共同隔离迟到结果与旧命令调用。

搜索只过滤内存中已加载模型，不查询 Shell、文件系统或网络。Slint 文本输入控件处理首字符、中文输入法组合、粘贴、退格和文本编辑；↑/↓/Enter/Esc 使用唯一当前项。Shell 命令始终以所属会话的原始 command ID 执行，展示文字不承担操作身份。复制、剪切、粘贴、重命名和删除继续进入 AsterFiles 任务中心；完整经典菜单继续作为动态、自绘、管理员命令和特殊扩展的兼容出口。

自动验证包括搜索大小写、中文、命令标识、空结果、分隔线整理、原始 command ID 保留、顶层不递归初始化子菜单和自有 verb 隔离；STA worker 的 Load/Invoke/Close 与真实扩展生命周期仍需人工结合日志复验。无界面状态写入 `artifacts/state/context-menu/search.json`。加载、迟到结果、调用和错误输出结构化日志；真实性能数据在用户手动复验时写入 `artifacts/perf/`。

2026-09-01 根据首次人工反馈完成第一项第二阶段修复：菜单改为 Windows 式紧凑密度（普通项 28px、分隔线 9px、搜索框 32px）；子菜单不再把父项误当命令执行，而是以独立 token 在原 STA 会话内发送 `WM_INITMENUPOPUP` 并按需读取一层。鼠标悬停 250ms 或点击展开，键盘右方向键展开、左方向键返回；叶子项始终保留原始 command ID，多层加载各自带请求代次，迟到、失败与耗时写入日志。搜索仍只覆盖已加载项目。

同日根据第二轮人工反馈修正子菜单悬停触发、逐行纵向锚点和按实际分隔线高度计算菜单内容区，避免子菜单固定出现在主菜单右上方及主菜单底部留白。STA worker 现在持续处理 Windows 消息；动态子菜单初始化后会短暂泵送并刷新菜单句柄，兼容 PowerShell 7 一类延迟填充项目。该兼容性仍需用户在真实 UI 中复验，自动验证不代替视觉与第三方扩展证据。

空白处背景菜单的 PowerShell 7 会比文件/文件夹菜单更晚完成动态填充。后续修复将同一子菜单 token 的重复悬停请求去重，并把空结果等待改为最多 300ms 的有限消息泵送；日志增加最终项目数，便于区分扩展确实返回空菜单与界面请求被替换。该等待只发生在用户展开子菜单后，不阻塞首次右键菜单外壳。

第二阶段其余部分尚未完成：普通 Shell 图标与快捷键列、STA 预热和活动目录空白菜单短缓存、100%–200% DPI/多屏边缘实证及完整无障碍复验。辅助进程隔离继续以真实慢加载或崩溃数据为决策依据，不在首个切片中预设。

## 1. 拆分原因

AsterFiles 当前已经提供自有基础菜单和“显示完整经典菜单”入口，可以调用 Windows 原生经典菜单。菜单后续可能涉及加载反馈、超时、辅助进程隔离、第三方扩展兼容和诊断，但这些问题与文件拖放、目录监听、隐藏文件及路径边界没有实施依赖。

在菜单方案尚未充分验证前，不把它绑定到 P3，也不为了赶阶段而引入临时隔离层或重复菜单。

## 2. 当前已有能力

- AsterFiles 第一层菜单提供新建、复制、剪切、粘贴、重命名、删除和永久删除等基础命令；
- “显示完整经典菜单”调用 Windows 原生经典菜单；
- 经典菜单支持空白处、单项、目录和多选上下文；
- Windows 和第三方 Shell 扩展命令由原生菜单承载；
- AsterFiles 接管的基础文件操作继续进入自己的任务中心；
- 当前实现保持不变，作为本 Feature 的行为基线。

## 3. 本 Feature 需要回答的问题

开始实现前必须先确认：

- 保持原生完整菜单作为唯一扩展入口，还是把部分 Windows/第三方命令投影到 AsterFiles 第一层菜单；
- 加载较慢时，界面应在哪里显示加载状态和已等待时间；
- Windows 整体生成菜单时，能够可靠诊断到什么粒度，不能伪造具体扩展名称；
- 超时后能否安全取消，还是只能隔离后放弃等待；
- 是否需要辅助进程，以及菜单对象、窗口消息、管理员命令和命令调用如何跨进程处理；
- 动态子菜单、自绘菜单、图标、属性、打开方式、在终端中打开和各类第三方扩展的兼容边界；
- 异常、崩溃和慢加载的日志内容及隐私边界；
- 当前“显示完整经典菜单”是否已经满足实际需求，是否值得承担改造成本。

## 4. 已确认的原则

- 不影响 AsterFiles 自带基础命令的可用性；
- 不用笼统且不可诊断的“部分菜单未加载”；
- 只有能从 Windows 获得可靠身份时才显示具体扩展名称；
- 不能为了显示扩展名称而重新发明一套与 Explorer 不一致的 Shell 菜单加载机制；
- Windows 原生完整菜单在新方案被真实验证前始终保留；
- 菜单模块与拖放、文件任务、目录监听保持独立。

## 5. 暂定验收方向

本 Feature 进入实施前另写完整方案和人工兼容矩阵。至少验证：

- 空白、单文件、单目录和多选菜单；
- 动态子菜单、自绘菜单和管理员命令；
- NanaZip/7-Zip、Git/TortoiseGit、PowerToys、杀毒软件等常见扩展；
- 慢加载、崩溃、超时和窗口关闭；
- 100%、150%、200% DPI 与多屏；
- 失败时 AsterFiles 主界面仍可使用，并有足够日志定位到可可靠获得的层级。

在这些设计和实证完成前，本 Feature 不承诺辅助进程、逐扩展状态或具体超时行为。
