# Feature：Windows Shell 菜单集成

> 日期：2026-08-31
> 状态：独立 Feature，设计待定；不属于 P3，不阻塞 P3

## 1. 拆分原因

AsterFiles 当前已经提供自有基础菜单和“显示完整经典菜单”入口，可以调用 Windows 原生经典菜单。菜单后续可能涉及加载反馈、超时、辅助进程隔离、第三方扩展兼容和诊断，但这些问题与文件拖放、目录监听、隐藏文件及路径边界没有实施依赖。

在菜单方案尚未充分验证前，不把它绑定到 P3，也不为了赶阶段而引入临时隔离层或重复菜单。

## 2. 当前已有能力

- AsterFiles 第一层菜单提供新建、复制、剪切、粘贴、重命名、删除和永久删除等基础命令；
- “显示完整经典菜单”调用 Windows 原生经典菜单；
- 经典菜单支持空白处、单项、目录和多选上下文；
- Windows 和第三方 Shell 扩展命令由原生菜单承载；
- AsterFiles 接管的基础文件操作继续进入自己的任务中心；
- 当前实现保持不变，作为本 Feature 的行为基线。

## 3. 本 Feature 需要回答的问题

开始实现前必须先确认：

- 保持原生完整菜单作为唯一扩展入口，还是把部分 Windows/第三方命令投影到 AsterFiles 第一层菜单；
- 加载较慢时，界面应在哪里显示加载状态和已等待时间；
- Windows 整体生成菜单时，能够可靠诊断到什么粒度，不能伪造具体扩展名称；
- 超时后能否安全取消，还是只能隔离后放弃等待；
- 是否需要辅助进程，以及菜单对象、窗口消息、管理员命令和命令调用如何跨进程处理；
- 动态子菜单、自绘菜单、图标、属性、打开方式、在终端中打开和各类第三方扩展的兼容边界；
- 异常、崩溃和慢加载的日志内容及隐私边界；
- 当前“显示完整经典菜单”是否已经满足实际需求，是否值得承担改造成本。

## 4. 已确认的原则

- 不影响 AsterFiles 自带基础命令的可用性；
- 不用笼统且不可诊断的“部分菜单未加载”；
- 只有能从 Windows 获得可靠身份时才显示具体扩展名称；
- 不能为了显示扩展名称而重新发明一套与 Explorer 不一致的 Shell 菜单加载机制；
- Windows 原生完整菜单在新方案被真实验证前始终保留；
- 菜单模块与拖放、文件任务、目录监听保持独立。

## 5. 暂定验收方向

本 Feature 进入实施前另写完整方案和人工兼容矩阵。至少验证：

- 空白、单文件、单目录和多选菜单；
- 动态子菜单、自绘菜单和管理员命令；
- NanaZip/7-Zip、Git/TortoiseGit、PowerToys、杀毒软件等常见扩展；
- 慢加载、崩溃、超时和窗口关闭；
- 100%、150%、200% DPI 与多屏；
- 失败时 AsterFiles 主界面仍可使用，并有足够日志定位到可可靠获得的层级。

在这些设计和实证完成前，本 Feature 不承诺辅助进程、逐扩展状态或具体超时行为。
