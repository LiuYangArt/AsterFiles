# Feature：Windows Shell 菜单集成

> 日期：2026-08-31
> 状态：Issue #13 已按用户确认的范围完成；目录空白菜单的 `Give access to` 兼容问题转入 [Issue #23](https://github.com/LiuYangArt/AsterFiles/issues/23)，当前暂时隐藏该无效入口；不属于 P3

## 0.3 Issue #21 附属弹窗承载（2026-09-02）

快速菜单外壳已从主窗口客户区迁到无边框 Windows 附属弹窗，菜单业务仍复用 #13 的 `QuickMenuState`、`ContextCommandRow`、Shell token 和原始 command ID。附属窗归属发起主窗，不进入任务栏和 Alt+Tab，不设全局置顶；Shell 的 owner 仍是所属主窗。主窗的 `context-menu-open` 继续作为统一会话真值。

定位链路把客户区点击点转换为物理屏幕坐标，并以目标显示器 `rcWork` 约束最终矩形：根菜单右下优先并按空间左右、上下翻转，子菜单从父项右侧展开、空间不足时向左翻转，过高时限制高度并滚动。窗口链保存 `WindowId + TabId + RequestId + generation + branch`，迟到请求、导航、所属窗口销毁、外部失焦和 Escape 都关闭整条链；主窗因附属窗获得焦点产生的 `Focused(false)` 不会误关菜单。

实现参考 Files 的 `FastContextFlyout.cs`：借鉴其物理像素、目标显示器工作区和真实布局后限高原则，不复制 WinUI `MenuFlyout` 或菜单内容模型。Files 没有可直接复制的 owner、层级、跨 DPI 重定位实现，这些行为保留为 AsterFiles Debug 人工验收项。代码记录首次/后续显示、重定位、子菜单展开和关闭耗时，真实数据由人工验收写入 `artifacts/perf/`。

人工反馈进一步确认定位语义：AsterFiles 主窗口边界不参与避让或翻转，菜单允许覆盖和跨出所属主窗；只有附属窗矩形接近目标显示器 `rcWork` 时才翻转或限高。附属菜单窗关闭 Windows 系统无边框阴影，由 Slint 自绘边框表达层级；主窗口和其他应用窗口的阴影策略不受影响。主窗口原生句柄只在打开菜单时读取。菜单 HWND 创建时已经带最终 owner、`WS_POPUP + WS_EX_TOOLWINDOW`、隐藏和无边框属性，避免先出现普通窗口框架再切换样式。根菜单与每层子菜单在内容、尺寸和位置就绪后先以 DWM cloak 状态显示，请求 Slint 首帧，并在保守的一帧合成边界后解除 cloak；失败、关闭或 owner 失效会先解除 cloak 再隐藏，避免不可见窗口残留焦点。

递归子菜单按深度保留一层一个附属窗口：同层切换只原子替换分支身份、行模型、尺寸和位置，不再隐藏并重建 HWND；进入更深层才使用下一槽，浅层换分支会隐藏并失效全部后代。回调按层动态读取当前分支身份，隐藏槽不参与焦点链；弹窗 generation 只校验窗口链事件，Shell 内容继续按 `session_id + request_id + submenu_request_id + token` 及当前导航身份拒绝迟到结果，两套代次不得互相替代。

附属窗迁移必须原样保持 HMENU 顶层顺序和现有异步语义：不在承载层排序、去重或按显示时点合并；`Loaded` 到达后替换骨架并按真实行数重新计算窗口高度和 `rcWork` 定位，`SubmenuLoaded` 继续按 token 替换对应分支，父项不充当叶子命令。人工复验暴露的同一 Shell 会话重复加载已修正：非空子菜单结果按原 token 缓存，窗口槽隐藏或复用不清缓存，重复打开直接投影；动态扩展超时返回的空结果不进入成功缓存，允许后续重试。每层槽独立保存行与活动项，快速跨行 timer 同时校验槽身份和目标行，避免父层/深层模型错配及双高亮。

## 0.1 Issue #24 实施状态（2026-09-02）

Issue #24 已完成代码、自动验证和用户真实 UI 验收。主菜单现在始终按“全部 AsterFiles 命令 → 单分隔线 → 全部 Windows 命令”组合；冷加载立即显示三行低对比度骨架，已有相同目录或选择快照时先显示变暗且完全不可交互的缓存行，准确 Shell 会话就绪后原位替换。菜单外框按真实行数变化，没有为 Windows 区域增加固定高度或独立滚动。

每个窗口保留独立快速菜单状态，并按 `WindowId + TabId + RequestId + 原始目录/选择路径` 隔离短期展示快照。350ms 空闲预热只覆盖当前活动目录或稳定选择；Windows 执行仍绑定最新会话与原始 command ID。STA worker 改为有界多会话存储，预热、多个窗口和当前可执行菜单不再互相覆盖；导航、选择变化、关闭和淘汰仍按会话精确释放。背景菜单顶层通过严格限定的 PowerShell 7 注册结构直接预载两个稳定子项，因此不再进入最多 300ms 的动态等待；执行时直接启动已验证的 pwsh.exe，原始目录单独传递，管理员项使用系统 runas，不执行注册表命令原文。结构不符合预期时回退原生 Shell。

自动验证覆盖菜单分组、占位/缓存禁用状态、原始 command ID、会话隔离与有界淘汰；用户已完成真实 UI 验收。Issue #23 的 `Give access to` 兼容问题不在本 Issue 范围。

## 0. Issue #13 实施状态（2026-09-01）

采用“Slint 快速菜单外壳 + Windows 经典菜单数据”。当前 Debug 已完成第一阶段：右键立即显示搜索框和 AsterFiles 自有命令；专用可复用 STA 工作线程在同一线程创建、使用和释放 `IContextMenu`/`HMENU`，后台读取顶层普通项目；会话标识、菜单请求代次、标签与目录请求身份、原始路径和选择快照共同隔离迟到结果与旧命令调用。

搜索只过滤内存中已加载模型，不查询 Shell、文件系统或网络。Slint 文本输入控件处理首字符、中文输入法组合、粘贴、退格和文本编辑；↑/↓/Enter/Esc 使用唯一当前项。Shell 命令始终以所属会话的原始 command ID 执行，展示文字不承担操作身份。复制、剪切、粘贴、重命名和删除继续进入 AsterFiles 任务中心；冗余的完整经典菜单入口已移除，无法可靠投影的动态、自绘和特殊扩展记录明确诊断。

自动验证包括搜索大小写、中文、命令标识、空结果、分隔线整理、原始 command ID 保留、顶层不递归初始化子菜单和自有 verb 隔离；STA worker 的 Load/Invoke/Close 与真实扩展生命周期仍需人工结合日志复验。无界面状态写入 `artifacts/state/context-menu/search.json`。加载、迟到结果、调用和错误输出结构化日志；真实性能数据在用户手动复验时写入 `artifacts/perf/`。

2026-09-01 根据首次人工反馈完成第一项第二阶段修复：菜单改为 Windows 式紧凑密度（普通项 28px、分隔线 9px、搜索框 32px）；子菜单不再把父项误当命令执行，而是以独立 token 在原 STA 会话内发送 `WM_INITMENUPOPUP` 并按需读取一层。鼠标悬停 250ms 或点击展开，键盘右方向键展开、左方向键返回；叶子项始终保留原始 command ID，多层加载各自带请求代次，迟到、失败与耗时写入日志。搜索仍只覆盖已加载项目。

同日根据第二轮人工反馈修正子菜单悬停触发、逐行纵向锚点和按实际分隔线高度计算菜单内容区，避免子菜单固定出现在主菜单右上方及主菜单底部留白。STA worker 现在持续处理 Windows 消息；动态子菜单初始化后会短暂泵送并刷新菜单句柄，兼容 PowerShell 7 一类延迟填充项目。该兼容性仍需用户在真实 UI 中复验，自动验证不代替视觉与第三方扩展证据。

空白处背景菜单的 PowerShell 7 会比文件/文件夹菜单更晚完成动态填充。后续修复将同一子菜单 token 的重复悬停请求去重，并把空结果等待改为最多 300ms 的有限消息泵送；日志增加最终项目数，便于区分扩展确实返回空菜单与界面请求被替换。该等待只发生在用户展开子菜单后，不阻塞首次右键菜单外壳。

第三轮人工复验确认空白处 PowerShell 7 仍只短暂显示加载状态。背景 Shell 菜单在 `WM_INITMENUPOPUP` 前还依赖根菜单的 `WM_INITMENU` 初始化；快速菜单现补齐与原生菜单一致的两段初始化消息，仍在所属 STA 会话和原始 HMENU 上执行。

第四轮复验后增加真实 Shell 探针，确认差异来自 PowerShell 7 的注册方式：文件夹对象菜单由 `IContextMenu` 正常返回两个子项，而目录空白背景菜单只返回一个带 `ExtendedSubCommandsKey` 的空占位 HMENU，向同一接口发送初始化消息也不会填充。快速菜单仅在 Shell 子菜单最终为空且顶层 verb 能精确映射到 `Directory\Background\shell` 时读取该系统级联定义，保留“Open here”和带 UAC 的管理员入口；其他动态扩展继续走原 STA Shell 会话，无法可靠投影时记录诊断。

目录空白菜单的 `Give access to` 与 PowerShell 7 看似都是子菜单，但来源不同：PowerShell 7 可由稳定的系统级联定义投影；`windows.share` 依赖动态 Shell 扩展。无界面探针能够读到共享子项，真实 UI 链路却仍会得到空投影。Issue #13 收尾时删除了未能解决问题的文件夹等价会话和命令重映射，仅在目录空白菜单隐藏该无效入口；文件夹对象菜单不受影响。根因诊断和恢复条件由 [Issue #23](https://github.com/LiuYangArt/AsterFiles/issues/23) 独立跟踪。

普通 Shell 图标与快捷键列、跨次缓存、DPI/多屏边缘和完整无障碍实证不阻塞本次用户确认的交付范围，后续按独立需求跟踪。辅助进程隔离仍只依据真实慢加载或崩溃数据决定。

## 1. 拆分原因

AsterFiles 当前已经提供自有基础菜单和可搜索的 Windows Shell 菜单投影。菜单后续可能涉及加载反馈、超时、辅助进程隔离、第三方扩展兼容和诊断，但这些问题与文件拖放、目录监听、隐藏文件及路径边界没有实施依赖。

在菜单方案尚未充分验证前，不把它绑定到 P3，也不为了赶阶段而引入临时隔离层或重复菜单。

## 2. 当前已有能力

- AsterFiles 第一层菜单提供新建、复制、剪切、粘贴、重命名、删除和永久删除等基础命令；
- Windows Shell 顶层普通项和普通子菜单直接投影到快速菜单；
- 经典菜单支持空白处、单项、目录和多选上下文；
- Windows 和第三方 Shell 扩展命令由原生菜单承载；
- AsterFiles 接管的基础文件操作继续进入自己的任务中心；
- 当前实现保持不变，作为本 Feature 的行为基线。

## 3. 本 Feature 需要回答的问题

开始实现前必须先确认：

- 保持原生完整菜单作为唯一扩展入口，还是把部分 Windows/第三方命令投影到 AsterFiles 第一层菜单；
- 加载较慢时，界面应在哪里显示加载状态和已等待时间；
- Windows 整体生成菜单时，能够可靠诊断到什么粒度，不能伪造具体扩展名称；
- 超时后能否安全取消，还是只能隔离后放弃等待；
- 是否需要辅助进程，以及菜单对象、窗口消息、管理员命令和命令调用如何跨进程处理；
- 动态子菜单、自绘菜单、图标、属性、打开方式、在终端中打开和各类第三方扩展的兼容边界；
- 异常、崩溃和慢加载的日志内容及隐私边界；
- 无法可靠投影的动态、自绘扩展如何诊断和处理。

## 4. 已确认的原则

- 不影响 AsterFiles 自带基础命令的可用性；
- 不用笼统且不可诊断的“部分菜单未加载”；
- 只有能从 Windows 获得可靠身份时才显示具体扩展名称；
- 不能为了显示扩展名称而重新发明一套与 Explorer 不一致的 Shell 菜单加载机制；
- Windows 原生完整菜单在新方案被真实验证前始终保留；
- 菜单模块与拖放、文件任务、目录监听保持独立。

## 5. 暂定验收方向

本 Feature 进入实施前另写完整方案和人工兼容矩阵。至少验证：

- 空白、单文件、单目录和多选菜单；
- 动态子菜单、自绘菜单和管理员命令；
- NanaZip/7-Zip、Git/TortoiseGit、PowerToys、杀毒软件等常见扩展；
- 慢加载、崩溃、超时和窗口关闭；
- 100%、150%、200% DPI 与多屏；
- 失败时 AsterFiles 主界面仍可使用，并有足够日志定位到可可靠获得的层级。

在这些设计和实证完成前，本 Feature 不承诺辅助进程、逐扩展状态或具体超时行为。
